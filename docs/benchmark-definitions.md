# Benchmark definitions

Each supported CIS benchmark is a versioned JSON file in `benchmarks/`. The
runtime never parses CIS documents: it validates a definition, then evaluates
each control with the check provider the definition names. Definitions are
generated by `tools/build_benchmark_definition.py` from the CIS PDF and a
specification module in `tools/specs/`.

## File layout

```json
{
  "schema_version": "1.0",
  "generated_by": "build_benchmark_definition.py",
  "benchmark": { ... },
  "controls": [ ... ],
  "manual_recommendations": [ ... ]
}
```

### `benchmark`

| Field | Meaning |
| --- | --- |
| `id`, `framework`, `name`, `short_name`, `version`, `published`, `source_document` | Identity of the CIS benchmark. `short_name` and `version` form the CIS mapping shown in reports (`CIS Debian Linux 13 \| 1.1.0 \| 5.1.22`). |
| `platform.os_id` | `/etc/os-release` `ID` (`debian`) or `esxi`. |
| `platform.version_ids` | Major versions the definition matches exactly (`["13"]`, `["8"]`). |
| `platform.architectures` | Informational. |
| `profiles` | Every profile named by the controls. Linux: `Level 1 - Server` … `Level 2 - Workstation`. ESXi: `Level 1 (L1) - Corporate/Enterprise Environment (general use)` and `Level 2 (L2) - High Security/Sensitive Data Environment (limited functionality)`. |
| `automated_control_count`, `manual_control_count` | Must equal the array lengths. |

### `controls[]` (automated recommendations)

| Field | Meaning |
| --- | --- |
| `id` | Stable check ID: `<prefix>-<section code>-<nnn>`, numbered in CIS order within the section (manual recommendations take numbers too, so IDs do not shift when a recommendation changes status). Prefixes: `LNX` (Debian), `ESX8`, `ESX7`. |
| `cis_id`, `title`, `profiles` | From the CIS document. |
| `section`, `category` | Report grouping (`service` and `category` in the m365 model). |
| `automated` | Always `true`. |
| `severity` | `Critical`, `High`, `Medium` or `Low` (risk-based, independent of the CIS level). |
| `description`, `rationale`, `business_impact`, `recommendation`, `remediation`, `references` | Independently written guidance. |
| `cis_controls_v8`, `nist_800_53` | Framework mappings taken from the CIS document. |
| `applies_if` | Optional list of conditions; the first one that does not hold makes the control `NOT_APPLICABLE` with its reason. |
| `notes` | Optional `{platform tag: text}`; the text is appended to the observation on that platform (for example `proxmox`). |
| `check` | `{"type": "<provider>", ...parameters}`. |

### `manual_recommendations[]`

`id`, `cis_id`, `title`, `section`, `category`, `profiles`, `severity`
(`Informational`), `guidance`, `remediation`, `references`,
`cis_controls_v8`, `nist_800_53`. Reports list them as limitations, and
`--include-manual` adds them as `NOT_ASSESSED` results.

## Validation

`lsa.engine.load_definition` rejects a definition before any evidence is
collected when a required field is missing, the declared counts do not match,
an ID or CIS number is duplicated, a control is not marked automated, a
severity is invalid, a control names a profile outside `benchmark.profiles`, or
a check type, condition or path source is not registered.

`benchmarks/catalog.json` lists each definition with its SHA-256. When the
catalog is missing or does not match the files, the tool prints a warning and
reads the definitions directly, so a stale catalog cannot select the wrong
file.

## Evaluation contract

- A provider receives the `System` (cached, read-only host access) and the
  `check` object, and returns PASS or FAIL with an observation, evidence and
  affected resources.
- Evidence that cannot be read raises `EvidenceUnavailable`, which becomes
  `NOT_ASSESSED` with the reason and, where relevant, the missing privilege.
- Any other exception becomes `ERROR` for that control only; the run
  continues.
- Conditions follow the same rules, so a condition that cannot be evaluated
  leaves the control `NOT_ASSESSED` rather than guessing.

### ESXi provider parameters

| Provider | Parameters | Evidence |
| --- | --- | --- |
| `esxi_advanced` | `settings`: list of `{key, rule, expected}`; rules use the operators below. | `vim-cmd hostsvc/advopt/view <key>`, falling back to `esxcli system settings advanced list -o /<path>` |
| `esxi_service_disabled` | `service` (service key such as `TSM-SSH`), `label`, `audit_channel` (note that the service may be running because the assessment uses it) | Service blocks of `vim-cmd hostsvc/hostconfig` (fallback: init scripts and `chkconfig`) |

| `esxi_vswitch_security` | `policy` (`forged`, `mac` or `promiscuous`), `label` | `esxcli network vswitch standard [portgroup] policy security get` |
| `esxi_portgroup_vlan` | `forbid` (VLAN IDs), `native_vlan` (use `esxi_native_vlan`), `what`, `note_vlans` (listed, not failed) | `esxcli network vswitch standard portgroup list` |
| `vmx_setting` | `key`, `expected` (`TRUE`/`FALSE` compared as booleans, numbers as numbers), `missing_ok` | Registered VMs' `.vmx` files |
| `vmx_device_absent` | `device_regex` (device prefix of a `<device>.present` key), `label`, `cdrom_only` | Registered VMs' `.vmx` files |
| `vmx_disk_mode` | `modes` (disk modes that fail) | `<bus>X:Y.mode` keys in the `.vmx` files |

esxcli CSV columns are matched after lower-casing and removing spaces, so
`VLAN ID`, `VLANID` and `VlanId` are the same column.

### Rule operators

`equals` (case-insensitive), `in`, `bool`, `min`, `max`, `range`, `positive`,
`zero_or_min`, `not_equal` and `present` (any non-empty value).

## Building a definition

```bash
python tools/build_benchmark_definition.py --spec <name> --pdf <CIS PDF>
python tools/build_benchmark_definition.py --spec <name> --text <extracted text>   # text with "=== PDF PAGE n ===" markers
```

The builder:

1. Extracts the PDF text (PyMuPDF, or pypdf as a fallback) and parses every
   recommendation header, its profile block, the CIS Controls v8 table and any
   NIST SP 800-53 references.
2. Loads the specification modules listed for `<name>` in `SPEC_MODULES`.
3. Fails when an Automated recommendation has no specification, a
   specification has no Automated recommendation, a Manual recommendation has
   no guidance (unless `AUTO_MANUAL_GUIDANCE` is set), or a platform note names
   an unknown recommendation.
4. Writes the definition, validates it with the runtime loader and rewrites
   `benchmarks/catalog.json`.

A specification module provides:

| Name | Purpose |
| --- | --- |
| `BENCHMARK` | The `benchmark` block plus `output_file`. |
| `SECTIONS` | `(CIS prefix, section, category, ID code)`; the longest matching prefix wins. |
| `CONTROLS` | `{cis_id: {severity, check, description, rationale, business_impact, recommendation, remediation, references, applies_if}}`. |
| `MANUAL` | `{cis_id: {guidance, remediation, references}}` for Manual recommendations. |
| `ID_PREFIX` | Optional; default `LNX`. |
| `AUTO_MANUAL_GUIDANCE`, `MANUAL_REFERENCES` | Optional; generate a generic review note for Manual recommendations. |
| `NOTES` | Optional `{cis_id: {platform tag: text}}`. |

`tools/specs/esxi_common.py` holds the ESXi topics shared by the ESXi 7.0 and
8.0 benchmarks; `esxi7.py` and `esxi8.py` map CIS numbers and severities onto
them.

## Adding a benchmark

1. Write the specification module(s) and register them in `SPEC_MODULES`.
2. If a check needs new evidence, add a provider decorated with
   `@provider("name")` in `lsa/checks/` (and import the module in
   `lsa/checks/__init__.py`). Providers must only read and must raise
   `EvidenceUnavailable` when evidence is missing. Return what was examined in
   the outcome's evidence, and use `System.record` for collector-level data
   that belongs in the Raw Evidence sheet.
3. Build the definition and add tests with a synthetic host under `tests/`.
4. If the new platform needs detection, extend `lsa/platform.py`; selection
   uses `platform.os_id` and `platform.version_ids` from the definition, so a
   new release of a supported platform needs no code change.
